[![License: CC BY-NC-ND 4.0](https://img.shields.io/badge/License-CC%20BY--NC--ND%204.0-lightgrey.svg)](https://creativecommons.org/licenses/by-nc-nd/4.0/deed.uk)


REST API, який показує, як за обраний період змінилася купівельна спроможність фіксованої суми в українських гривнях (UAH) порівняно з інфляцією та різними фінансовими інструментами для пасивного збереження заощаджень (див. розділ 1, «Підтримувані інструменти»).  

**Статус:** рання робоча версія (Minimum Viable Product).

---

## 1. Призначення

Сервіс відповідає на запитання: «Що сталося з моїми грошима, якщо я просто тримав їх у гривні, і як це виглядає на тлі альтернатив?». Ви задаєте суму в гривнях і період, а у відповідь отримуєте:

| Поле відповіді | Що означає |
| :--- | :--- |
| `cashGrivna` | Номінальна сума, яка не змінилася («гроші під матрацом»). |
| `inflationEquivalent` | Скільки гривень знадобилося б наприкінці періоду, щоб купити те саме, що на початкову суму на початку періоду. |
| `usdEquivalent` | Скільки гривень вийшло б, якби на початку періоду всю суму було обміняно на долари, а наприкінці назад на гривні. |
| `eurEquivalent` | Те саме для євро. |

**Як оцінити результат.** Якщо `usdEquivalent` вищий за `inflationEquivalent`, то зберігання в доларах захистило капітал від інфляції краще, ніж номінальна гривня. Якщо `cashGrivna` нижча за `inflationEquivalent`, то гроші «під матрацом» втратили купівельну спроможність.

### Підтримувані інструменти

| Категорія | Код | Опис | Дані доступні з |
| :--- | :--- | :--- | :--- |
| `Inflation` | `CPI` | Індекс споживчих цін (Consumer Price Index) | січень 2000 |
| `Currencies` | `USD` | Долар США, комерційний курс UAH/USD | вересень 1996 |
| `Currencies` | `EUR` | Євро, комерційний курс UAH/EUR | січень 1999 |

**Актуальність даних по інструментах:** по 2026-06 включно.

## 3. API

### `GET /api/calculator/compare`

#### Параметри запиту

| Параметр | Тип | Обов'язковий | Опис | Приклад |
| :--- | :--- | :--- | :--- | :--- |
| startDate | string (yyyy&#8209;MM&#8209;dd) | так | Початок періоду. Враховуються лише рік і місяць, дата нормалізується до 1-го числа. | 2023&#8209;01&#8209;01 |
| endDate | string (yyyy&#8209;MM&#8209;dd) | так | Кінець періоду (також лише рік і місяць). | 2023&#8209;02&#8209;01 |
| amount | decimal | так | Вихідна сума в UAH, строго більша за 0. | 1000 |

#### Правила валідації (помилка `400`)

* `amount` > 0;
* `startDate` ≤ `endDate`;
* `startDate` не раніше вересня 1996 (спільна межа для всіх інструментів, запровадження гривні);
* `endDate` не пізніше поточного місяця (за UTC).

> Межі за окремими інструментами (EUR з 1999-01, CPI з 2000-01) **не** призводять до помилки. У такому разі відповідь `200`, значення інструмента дорівнює `null`, а причину вказано в `warnings`.

#### Приклад запиту

```http
GET /api/calculator/compare?startDate=2011-01-01&endDate=2011-02-01&amount=1000 HTTP/1.1
Host: localhost:7241
```

#### Успішна відповідь (`200 OK`)



```json
{
  "startDate": "2011-01-01",
  "endDate": "2011-02-01",
  "initialAmount": 1000,
  "summary": {
    "cashGrivna": 1000,
    "inflationEquivalent": 1019.09,
    "usdEquivalent": 997.5,
    "eurEquivalent": 1028.38
  },
  "warnings": []
}
```

Контрольный расчет:

| Інструмент | Значення на<br>стартову дату | Значення на<br>кінцеву дату | Розрахунок / Результат |
| --- | --- | --- | --- |
| **CPI** | 1,01  | 1,009 | <nobr>1000*1,01*1,009=1019,09</nobr>|
| **USD** | 7,99  | 7,97  | <nobr>1000/7,99*7,97=997,50</nobr>|
| **EUR** | 10,57 | 10,87 | <nobr>1000/10,57*10,87=1028,38</nobr>|

#### Відповідь із попередженнями (часткові дані)

Якщо запитаний період виходить за межі доступних даних за інструментом, відповідне поле `summary` дорівнює `null`, а причину вказано в `warnings`.

```json
{
  "startDate": "1997-01-01",
  "endDate": "2023-01-01",
  "initialAmount": 10000,
  "summary": {
    "cashGrivna": 10000,
    "inflationEquivalent": null,
    "usdEquivalent": 213421.05,
    "eurEquivalent": null
  },
  "warnings": [
    "Historical inflation data for 'CPI' is available only starting from 2000-01, but 1997-01 was requested.",
    "Historical exchange rate data for 'EUR' is available only starting from 1999-01, but 1997-01 was requested."
  ]
}
```

#### Обробка помилок

Помилки повертаються у форматі [RFC 7807](https://datatracker.ietf.org/doc/html/rfc7807) (`ProblemDetails`).

| Статус | `title` | Коли виникає |
| :--- | :--- | :--- |
| `400` | `Validation Error` | Порушено правила валідації. Подробиці в полі `errors`. |
| `400` | `Domain Error` | Порушено доменне правило (текст у `detail`). |
| `400` | (стандартний ASP.NET Core) | Параметр не вдалося розібрати, наприклад, неправильний формат дати. Формат тіла стандартний для ASP.NET Core (`ValidationProblemDetails`). |
| `500` | `Server Error` | Непередбачена помилка. Внутрішні деталі клієнту не передаються. |

Приклад `400 Validation Error` для `amount=0`:

```json
{
  "title": "Validation Error",
  "status": 400,
  "detail": "One or more validation failures have occurred.",
  "instance": "/api/calculator/compare",
  "errors": {
    "Amount": ["Amount must be greater than zero."]
  }
}
```

## 4. Методологія розрахунків і дані

### 4.1. Формули

| Показник | Формула |
| :--- | :--- |
| ІСЦ (`inflationEquivalent`) | `amount × ∏ rate`, добуток місячних коефіцієнтів за всі місяці діапазону |
| Валюта (`usdEquivalent`, `eurEquivalent`) | `amount ÷ rate_start × rate_end`, де `rate` — курс у гривнях за одиницю валюти |

Результати округлюються до 2 знаків після коми.

Приклад на тестових даних: `1000 × 1.01 × 1.02 = 1030.20` для ІСЦ і `1000 ÷ 36.5 × 37.0 = 1013.70` для USD.

**Які місяці входять до періоду.** Для ІСЦ застосовуються коефіцієнти кожного місяця діапазону, **включно з початковим і кінцевим**. Для валют беруться два значення: курс початкового і курс кінцевого місяця. Тому за `startDate = endDate` валютний еквівалент дорівнює вихідній сумі, а ІСЦ-еквівалент дорівнює сумі, помноженій на коефіцієнт цього місяця. Це опис поточної реалізації.

### 4.2. Формат даних

| Дані | Поле `Rate` | Приклад |
| :--- | :--- | :--- |
| Інфляція | Місячний множник відносно попереднього місяця | `1.012` означає +1,2% за місяць |
| Курси валют | Гривні за 1 одиницю валюти | `36.5` означає 36,5 UAH за 1 USD |

Усі дати зберігаються нормалізованими до першого числа місяця (`yyyy-MM-01`). 
Пара «валюта + місяць» і місяць інфляції унікальні (унікальні індекси в БД). Дублікати під час імпорту даних відхиляються з помилкою.
Набори даних безперервні: для кожного місяця всередині доступного діапазону є значення. Розрахунок спирається на цю умову; якщо пропуск усе ж виникне, ІСЦ поверне `null` з попередженням про неповні дані, а не рахуватиме за неповним рядом.

### 4.3. Методологічні рішення

**Середньомісячні курси.** Валютні розрахунки спираються на середньомісячні курси, а не на щоденні котирування. Незалежно від дня в запиті застосовується курс за весь місяць. Для макроаналізу купівельної спроможності зберігання щоденних котирувань є надлишковим, а помісячних даних достатньо, щоб оцінити довгострокові тенденції.

**Комерційний, а не офіційний курс.** Використовуються комерційні (ринкові) курси, а не офіційний курс НБУ. В історії України були періоди помітного розходження між офіційним і реальним курсом обміну, і саме ринковий курс відображає, за яким курсом можна було обміняти валюту.

**Два ступені обмежень за датами:**

1. *Спільна межа (помилка 400).* Дата початку раніше вересня 1996 відхиляється валідатором до запуску розрахунку. Доменні сутності `ExchangeRate` і `InflationRate` додатково захищають ті самі межі під час створення записів, наприклад, під час сидингу.
2. *Межа інструмента (попередження).* Якщо запитаний період виходить за межі даних за конкретним інструментом, розрахунок за ним не виконується, значення дорівнює `null`, а в `warnings` зазначається причина. Решта інструментів рахуються як зазвичай.

## 5. Архітектура

Проєкт побудовано як шаровий застосунок у дусі Clean Architecture. Шар Application працює з даними через абстракцію `IApplicationDbContext` поверх EF Core. Це прагматичний компроміс: DbContext уже реалізує патерни Unit of Work і Repository, тому окремий шар репозиторіїв не вводився.

### 5.1. Структура рішення

```
InflationMonitor/
├── InflationMonitor.Domain/        # Сутності, доменні правила (інваріанти), доменні винятки
├── InflationMonitor.Application/   # Запити й обробники (MediatR), стратегії розрахунку, фабрика,
│                                   # DTO, валідація (FluentValidation), кешування
├── InflationMonitor.Persistence/   # EF Core, конфігурації сутностей, SQLite, сидинг із JSON
├── InflationMonitor.WebApi/        # Контролери, Swagger, глобальний обробник помилок, Program.cs
└── InflationMonitor.Tests/         # Модульні та інтеграційні тести (xUnit)
```

Напрямок залежностей: `Domain` ← `Application` ← `Persistence` і `WebApi`.

### 5.2. Шлях запиту

```
HTTP GET → ComparisonController
         → MediatR → ValidationBehavior (FluentValidation) → CalculateComparisonQueryHandler
         → FinancialInstrumentFactory → InflationStrategy / BatchCurrencyStrategy
         → IMemoryCache → (у разі промаху) SQLite через EF Core
```

Будь-який виняток перехоплюється `GlobalExceptionHandler` і перетворюється на `ProblemDetails`.

### 5.3. Технологічний стек

| Технологія | Роль |
| :--- | :--- |
| .NET / ASP.NET Core | Веб-API |
| MediatR | Диспетчеризація запитів, наскрізна функціональність через pipeline behaviors |
| FluentValidation | Валідація запиту до виклику обробника (fail-fast) |
| Entity Framework Core + SQLite | Зберігання історичних даних, конфігурації через `IEntityTypeConfiguration<T>` |
| `IMemoryCache` | Кешування історичних даних |
| Swagger / OpenAPI | Інтерактивна документація (у середовищі Development) |
| xUnit, Moq, FluentAssertions | Тестування |

У запитах реалізовано лише «читальну» частину CQRS (розрахунки), команд, що змінюють дані, немає.

### 5.4. Ключові рішення

#### Стратегії та фабрика

Кожна категорія інструментів реалізує `IBatchFinancialInstrumentStrategy` (`InflationStrategy`, `BatchCurrencyStrategy`). `FinancialInstrumentFactory` обирає потрібну стратегію за ключем категорії. Нова категорія підключається новою стратегією та її реєстрацією в DI. При цьому структура відповіді (`FinancialComparisonSummaryDto`) і обробник запиту поки що знають про інструменти явно, тому додавання нового інструмента зачіпає і їх (див. розділ 7, «Відомі обмеження»).

#### Кешування

Для зниження навантаження на SQLite використовується `IMemoryCache` з такими параметрами:

* ліміт: 22 000 записів, вага кожного запису дорівнює 1;
* під час досягнення ліміту з кешу видаляється 20% записів (ущільнення);
* сканування прострочених записів раз на 15 хвилин;
* записи з історичними значеннями (ІСЦ, курси) живуть до 10 днів (абсолютний час життя);
* дата останніх доступних даних за валютою кешується окремо на 12 годин.

<details>
<summary>Обґрунтування ліміту 22 000</summary>

Це запас під майбутнє розширення: до 30 інструментів × 50 років × 12 місяців = 18 000 записів плюс технологічний запас. Фактично зараз (ІСЦ і дві валюти за кілька десятиліть) у кеші близько тисячі записів.

За оцінки близько 300 байтів на запис повний набір даних займав би близько 6 МБ. Це груба оцінка, реальне споживання залежить від накладних витрат `MemoryCache`. Таким чином, увесь історичний зріз має вміститися в пам'ять, а споживання залишається скромним.

</details>

<details>
<summary>Чому такий час життя записів</summary>

Історичні значення за минулі місяці за задумом не змінюються: дані лише накопичуються (append-only), тому тривале зберігання в кеші безпечне і прискорює розрахунки. Кеш зберігається в пам'яті одного процесу.

</details>

#### Обробка помилок

`GlobalExceptionHandler` логує винятки та перетворює їх на `ProblemDetails`: помилки валідації та доменні помилки стають відповіддю `400`, решта відповіддю `500` із узагальненим повідомленням, щоб не розкривати внутрішні деталі. Помилки прив'язки параметрів (наприклад, неправильний формат дати) обробляє сам ASP.NET Core.

## 7. Відомі обмеження та плани

### Відомі обмеження

* **Точність — один місяць.** Дні всередині місяця не враховуються, хоча формат параметрів містить день.
* **Немає оновлення даних.** Дані завантажуються з JSON лише в порожні таблиці. Автоматичного імпорту нових місяців немає, тому дані потрібно оновлювати вручну.
* **Міграції та сидинг лише в Development.** Для інших середовищ порядок розгортання бази потрібно організувати окремо.
* **Кеш не розділяється між екземплярами.** Він локальний для процесу. Після оновлення даних у БД значення в кеші можуть застарівати до 10 днів.
* **Розширення інструментів потребує правок контракту.** Новий інструмент означає нову стратегію, а також зміну DTO відповіді та обробника запиту.
* **Пропущені параметри.** Відсутній параметр не відхиляється на етапі прив'язки, підставляється значення за замовчуванням, і спрацьовує звичайна валідація. Текст помилки в такому разі може бути неочевидним.

### Ідеї на майбутнє

Це ідеї, а не зобов'язання:

* державні облігації (`Bonds`);
* дорогоцінні метали (`PreciousMetals`);
* банківські депозити (`Deposits`), наприклад, середня ставка за річними депозитами фізичних осіб (`DEP_UAH_1Y`);
* фондові індекси (`MarketIndices`);
* криптовалюти;
* автоматичне оновлення даних.

Сервіс має виключно інформаційний характер і **не є фінансовою рекомендацією**. Розрахунки ґрунтуються на усереднених місячних даних і можуть відрізнятися від реальних результатів операцій з активами.

## 10. Ліцензія та контакти

Проєкт поширюється за ліцензією Creative Commons Attribution-NonCommercial-NoDerivatives 4.0 International (CC BY-NC-ND 4.0).

**Дозволено:**

* вивчати вихідний код;
* запускати проєкт локально для себе, навчання та некомерційних цілей;
* поширювати незмінені копії із зазначенням авторства та посиланням на ліцензію.

**Заборонено без письмового дозволу автора:**

* будь-яке комерційне використання, включно з платним доступом до розгорнутого API третіх осіб;
* поширення змінених версій і похідних робіт.

**Дані.** Ліцензія поширюється на вихідний код. Історичні дані в `Seeding/Data` отримано на основі сторонніх джерел (див. розділ 8), і на них діють умови використання цих джерел.
